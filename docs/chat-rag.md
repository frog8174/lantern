# 聊天：段落累積式 RAG

`features.chat_messages()` 決定每一題要附什麼內容給模型。`CHAT_CONTEXT` 控制做法：
- `auto`（預設）：本文說明的做法。
- `full`：舊做法，第一題就送整篇論文。

## 每一題的流程（`new_context()`）
1. **前面已經送過整篇**：這題什麼都不附。
2. **改送全文**，條件是論文放得下全文，而且符合下面任一條：
   - 這是同一段對話的第 8 題（`FULL_AFTER_TURNS`）；
   - 累積送出的段落超過全文的一半（`FULL_SENT_RATIO`）。

   這時改送全文比繼續檢索划算，之後每題只付快取讀取價。
3. **改寫＋分流**（`plan_question()`）：
   - 用 Haiku（`LLM_MODEL_QUERY`）讀最近 4 則對話和新問題，輸出 `{"query": 英文獨立檢索句, "scope": "local" | "global"}`。
   - 追問裡的「它」「那個方法」會換成對話中指的東西。
   - 改寫失敗就用原句，當成細節題。
4. **全篇性問題（global）**：
   - 有快取的摘要：附摘要。
   - 沒有摘要、但全文放得下：改送全文。
   - 其他情況：當成細節題，走第 5 步。
5. **細節題（local）**：
   - 用 `retrieval.search()` 取 8 段，**已經送過的段落不重送**。
   - 使用者正在看的那頁，第一次問到時附上。

## 為什麼要這樣設計
- **段落附在「這一題」的訊息裡**：前面幾題的訊息原封不動，對話前綴就不會變，提示詞快取接得上，下一題只為新增的部分付全價。附的內容存在 `messages.ctx`。全文不存文字，只存 `@full` 標記，組訊息時再展開。
- **追問看得到前文**：上一題附的段落還在對話裡，模型照樣看得到。
- **快取斷點放在最後兩則 user 訊息**（`llm._to_claude()`）：第一則斷點讓這題讀到上一題寫進快取的前綴，第二則把這題新加的內容寫進快取。
- **對話全部保留**：不再只帶最近 10 則訊息。滑動視窗每題都會改變前綴，快取永遠接不上。

## 評估（`uv run python -m eval.chat_eval`）
做法：4 篇論文，每篇一段 5 題的連續對話（細節、追問、細節、全篇、追問）。由 Sonnet 出題和評分，0～2 分。
結果：`eval/results/20261104-0945.md`（花費請看校正值）。

| | full | auto |
|---|---|---|
| 平均分 | 1.80 | 1.70 |
| 第 1 題（冷啟動）花費 | $0.054 | $0.0095 |
| 連續 5 題總花費 | $0.109／篇 | $0.101／篇 |

**結論**：
- auto 省錢靠的是冷啟動：第 1 題，或停超過 5 分鐘、快取過期後再問，便宜 5～6 倍。
- 一口氣連續追問時，兩者花費差不多。
- 品質差距在 20 題的雜訊範圍內。auto 的失分大多是檢索沒撈到細節。
- 要不要維持 `auto` 當預設，看用量記錄：一段對話平均幾題、兩題之間隔多久。
